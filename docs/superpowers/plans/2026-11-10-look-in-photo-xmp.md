# Look in the photo (XMP) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every JPG shot through COLOR 1–4 carries the applied look as named `cad:` fields in its XMP packet, and the Control Panel can read them back as a look.

**Architecture:** One machine-readable field list (`docs/xmp-fields.json`) drives three consumers: the Control Panel reader/formatter (`webapp/src/xmp.ts`), the firmware formatter (`xb_xmp` in the GUIDES.BIN code block, table generated by `build.py`), and the exiftool config. A hook at the stock JPEG XMP writer (0x60455cfa) calls the block, which captures the effective settings as a 64-byte `LOOKS.BIN` record (`pf_capto`, the way `xb_lkd` does) and rewrites the packet tail in the RAM buffer (0x62a982e6).

**Tech Stack:** TypeScript + vitest (`webapp/`), MN10300 assembly + Python (`firmware/`, built in the `om3-linux` container), Node emulator scripts (`tools/emulator/`).

**Spec:** `docs/superpowers/specs/2026-11-10-look-in-photo-xmp-design.md` (approved 2026-11-10). Firmware facts: `research/NOTES.md`, sections from "Writing the look into the picture's metadata" to "Rating, and where the look is at shot time". All firmware facts are *analysis* until Task 8 and the owner's camera test.

## Global Constraints

- The XMP packet stays exactly **2301 bytes**; `<?xpacket end="w"?>` stays last; the APP1 length constants (0x091C, return 2334) are not touched.
- Fields go **after the `xmp:Rating` digit** (the stock rating edit searches only the first 230 bytes), before `/>`.
- Namespace `xmlns:cad="https://androidfanman.github.io/caduceus-om3/ns/1/"`; `cad:Version="1"`.
- Values are one `LOOKS.BIN` record (`docs/FORMATS.md`), as applied at the shot; record `+42` (legacy Sharpness) is not written; no COLOR slot field.
- `Look` is the card's look/film name, up to 15 characters, with `& < > " '` and anything outside 0x20..0x7e replaced by `_`; omitted when no film is selected. `Film` = 5 × (COLOR − 1) + look (1–20), `0` for the slot's own settings.
- Written only when COLOR 1–4 is the effective profile; otherwise the stock packet is left byte-identical.
- GUIDES.BIN code block cap: 16448 B malloc (13248 B used by v0.26.2).
- No OM firmware, disassembly dumps or camera graphics in the repo. Firmware builds run in the container (a macOS build does not reproduce). The owner flashes; we prepare files only. No release without the owner's go-ahead.
- Commits: author and committer `androidfanman <androidfanman@users.noreply.github.com>` (`GIT_COMMITTER_NAME/EMAIL` env plus `-c user.name -c user.email`), with the session's attribution trailer. Stage only this plan's files (the working tree holds the owner's other uncommitted changes).
- Work on branch `feature/look-in-photo-xmp`; its README banner says "work in progress, not for use".

## Review Focus

1. A look name with `& < > " '` or non-ASCII characters → the packet stays valid XML (characters become `_`). Tested in Task 2 (TypeScript formatter) and Task 8 (firmware output).
2. A COLOR shot followed by a shot with no COLOR active → the second packet is the stock packet byte for byte (no stale fields). Task 8.
3. Every value at its extreme (longest possible text) → still exactly 2301 bytes, end marker last, no overrun. Task 6 (`build.py` worst-case size check) and Task 8.
4. A JPG with no XMP, no `cad:` fields, a truncated packet, or not a JPEG at all → plain message in the Control Panel, no crash. Task 2.
5. A photo whose `cad:` values are out of range or malformed (hand-edited) → refused with a message naming the field, never silently clamped. Task 2.
